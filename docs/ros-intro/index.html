Q1. ROS 是什么？

先把名字里的误会解掉

ROS = Robot Operating System，但它不是操作系统。

  • 它不管理内存、不调度进程、不提供文件系统 —— 那些是 Linux 干的活。
  • 它其实是一套中间件 + 工具链 + 一堆约定：
它提供它不提供
进程之间怎么通信（话题 / 服务 / 动作）进程调度、内存管理
数据怎么描述（.msg / .srv / IDL）实时内核
坐标怎么统一（tf2）硬件驱动（驱动要自己写/找）
一堆调试工具（ros2 topic / rqt / bag）控制算法

ROS 帮你解决的是「一堆程序怎么凑成一个机器人」这件事。

一个 ROS 程序长什么样

最小的工作单元叫节点（node），就是一个普通进程。

python
import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class Talker(Node):
    def __init__(self):
        super().__init__('talker')
        self.pub = self.create_publisher(String, 'chatter', 10)
        self.create_timer(0.5, self.tick)

    def tick(self):
        self.pub.publish(String(data='hello'))

rclpy.init()
rclpy.spin(Talker())
  • 没有 main 循环，没有 socket —— 你把「发什么」写出来就行。

Q2. 为什么机器人需要它？

先看不用 ROS 会怎样

假设你要做一台移动机器人，上面有这些程序：

  • 激光雷达驱动 → 里程计
  • 相机驱动 → 目标检测
  • 定位 → 路径规划 → 底盘控制

如果每个箭头都是一段自己写的 socket：

  • N 个程序两两通信，最多 N² 条链路要维护。
  • 换一个雷达，驱动接口变了，下游全改。
  • 想录一段数据回放调试？自己写。
  • 想看看当前谁在发什么？自己写。

最后你写出来的那坨东西，其实就是一个更差的 ROS。

解耦：谁也不知道对方是谁

用了 ROS 之后：

  • 发布者只管往话题上写，不知道有几个订阅者、它们是谁。
  • 订阅者只管从话题读，不知道数据从哪来。
  • 加一个新的「录制节点」不需要通知任何人。

这就是「解耦」的实际含义：把「谁跟谁说话」从代码里拿掉，交给运行时。

代价也在这里：出问题时你不能靠读一处代码搞明白，得去看运行时的图 —— rqt_graph 就是干这个的。

顺带解决的三件事

  1. 数据格式统一：.msg 定义了消息长什么样，生成各语言的代码。
  2. 时间与坐标统一：所有话题带时间戳，所有坐标系挂在同一棵 tf2 树上。
  3. 可回放：ros2 bag record -a 把一切录下来，之后离线重放， 离线调试比在真机上反复试高效得多。

ps：第三条是很多人低估的。能复现才是工程。

Q3. ROS 1 还是 ROS 2？

一句话结论

新项目一律 ROS 2。 ROS 1 已经在 2025 年 5 月停止维护（Noetic 是最后一个版本）。

主要差异

维度ROS 1ROS 2
通信底层自己写的 TCPROSDDS（工业级中间件）
实时性基本没有支持实时与确定性 QoS
多机 / 组播需要 master 协调天然支持，可发现
单点故障roscore 挂了全挂无中心节点
进程模型一个节点一个进程支持组合式节点（同进程多节点）
生命周期无托管节点（Lifecycle Node）
安全无SROS2（认证 + 加密）
平台主要 LinuxLinux / Windows / macOS / RTOS

DDS 意味着什么

  • ROS 1 的通信是「够用就好」；ROS 2 直接把工业界用了十几年的 DDS 拿来当底座。
  • 带来的是 QoS：可靠性、历史深度、期限、活跃度……全都可以按话题单独配。
  • 代价是复杂度：QoS 不匹配时连接根本建立不起来，而且默认不报错。
text
发布者 reliable  ←→  订阅者 best_effort   →  没有连接，也没有日志

这条坑在《节点和工具》那一篇里单独展开 —— 它是 ROS 2 新手最常见的一次「玄学」。

Q4. 一次通信长什么样？

时序

以「相机节点发布一帧图像，检测节点订阅」为例：

  • 两个节点启动，各自连上 DDS 的域（domain）
  • DDS 做发现：订阅者广播「我要 /image_raw」
  • 发布者收到，两边协商 QoS，协商通过才建立连接
  • 发布者调用 publish()，序列化后交给 DDS
  • DDS 按 QoS 决定：立刻发 / 排队 / 丢掉最旧的
  • 订阅者收到，反序列化，调用你的回调

注意第 3 步：协商不通过就没有第 4 步，而且不会有明显的报错。

试一个：模拟发布订阅

下面这段是可运行的。它把「话题」抽象成一个只有名字的邮箱 —— 发布者不知道谁在听，订阅者不知道谁在发，这正是 ROS 的解耦。

可运行示例JavaScript
// 极简 pub/sub：把「话题名 → 订阅者列表」放在一个中心表里
const bus = new Map();
function advertise(topic) {
  if (!bus.has(topic)) bus.set(topic, []);
  return { publish: (msg) => (bus.get(topic) || []).forEach(cb => cb(msg)) };
}
function subscribe(topic, cb) {
  if (!bus.has(topic)) bus.set(topic, []);
  bus.get(topic).push(cb);
  return () => bus.set(topic, bus.get(topic).filter(x => x !== cb));
}

// 相机节点：只管发
const cam = advertise('/image_raw');
// 检测节点：只管收
const stop = subscribe('/image_raw', (m) =>
  demo.log('检测节点收到第', m.seq, '帧，', m.kb, 'KB'));

// 中途再插一个「录制节点」—— 相机节点的代码一行没改
setTimeout(() => subscribe('/image_raw', (m) => demo.log('  录制节点也收到了第', m.seq, '帧')), 0);

let seq = 0;
const timer = setInterval(() => {
  cam.publish({ seq: ++seq, kb: 300 + seq * 7 });
  if (seq >= 4) { clearInterval(timer); stop(); demo.log('检测节点已退出，相机还在发 —— 它不知道'); }
}, 260);

把最后一行注释掉再跑一次，你会看到相机节点完全没有察觉。

小结

  1. ROS 是中间件 + 约定，不是操作系统。
  2. 它解决的核心问题是「一堆程序怎么凑成一个机器人」，手段是解耦。
  3. 新项目用 ROS 2，底座是 DDS，因此有 QoS，也因此有 QoS 的坑。
  4. 记住那次协商：QoS 谈不拢就没有连接，而且默认不报错。
