1. 话题 / 服务 / 动作

三种通信方式

话题 Topic服务 Service动作 Action
形状多对多，持续流一问一答长任务 + 中间反馈
阻塞不等等返回不等，可查询进度
可取消—不能能
典型用途传感器、状态开关、查询导航、抓取、标定
底层DDS pub/sub两个话题拼的三个话题拼的

动作其实就是「服务 + 反馈话题 + 取消话题」的封装。

怎么选：三个问题

  1. 频率高吗？ 高（>10 Hz）→ 话题。服务和动作的握手开销扛不住。
  2. 要等结果吗？ 要，而且很快（<1 s）→ 服务。
  3. 是做一件事，还是开一个任务？ 长任务（秒级以上、要进度、可能取消）→ 动作。
text
反例：用服务去控制底盘走 3 米。
   → 服务会阻塞，中途想停都停不下来。
   正解：用动作，或者直接发速度指令话题 + 自己看里程计。

一个容易忽略的点：消息会丢，状态不会

  • 话题的 QoS 里如果设了 best_effort，丢几帧是正常设计，不是 bug。
  • 所以「必须不丢」的东西别只发一次：要么用 reliable， 要么改成周期性地发状态（发布/订阅的心跳式设计）。

机器人上最常见的事故是：发了一次「使能」，然后假设它到了。

2. QoS：ROS 2 最容易踩的坑

它是什么

QoS（Quality of Service）是一组通信契约。发布方和订阅方各自声明自己的要求， DDS 只在兼容时才建立连接。

那几个维度

策略取值影响
Reliabilityreliable / best_effort要不要重传
Durabilityvolatile / transient_local后加入的订阅者能不能拿到历史
Historykeep_last(n) / keep_all队列里留几条
Depth整数keep_last 的深度
Deadline时长多久没数据算「超期」
Lifespan时长消息多久后作废
Liveliness自动 / 手动怎么判断对方还活着

transient_local 特别有用：晚启动的节点也能拿到最后一次「地图」「参数」这类 只发一次的消息。

兼容规则（背下来能省很多时间）

  • 发布者的承诺必须 ≥ 订阅者的要求：
    • 订阅者要 reliable → 发布者必须 reliable。（反过来可以）
    • 订阅者 keep_last(n) → 发布者深度要 ≥ n。
    • 订阅者要 deadline → 发布者也得支持。
  • 不兼容时：没有连接、没有回调、默认也没有日志。
bash
# 唯一有效的排查手段
ros2 topic info /image_raw --verbose     # 看两边的 QoS
ros2 doctor --report                     # 看全局有没有异常

试一个：QoS 匹配

下面这段模拟 DDS 的协商过程。改改策略组合，看看哪些能连上。

可运行示例JavaScript
// 兼容 = 发布者的承诺能不能满足订阅者的要求
function compatible(pub, sub) {
  const why = [];
  const rank = { best_effort: 0, reliable: 1 };
  if (rank[pub.reliability] < rank[sub.reliability])
    why.push(`可靠性：发布者 ${pub.reliability} < 订阅者 ${sub.reliability}`);
  if (pub.depth < sub.depth)
    why.push(`深度：发布者 ${pub.depth} < 订阅者 ${sub.depth}`);
  if (sub.durability === 'transient_local' && pub.durability !== 'transient_local')
    why.push('持久性：订阅者要历史，发布者只发当下');
  return why;
}

const cases = [
  ['传感器图像（高频、允许丢）',
    { reliability: 'best_effort', depth: 1, durability: 'volatile' },
    { reliability: 'best_effort', depth: 1, durability: 'volatile' }],
  ['订阅者要可靠，发布者尽力而为',
    { reliability: 'best_effort', depth: 10, durability: 'volatile' },
    { reliability: 'reliable', depth: 10, durability: 'volatile' }],
  ['后启动的节点要地图',
    { reliability: 'reliable', depth: 1, durability: 'volatile' },
    { reliability: 'reliable', depth: 1, durability: 'transient_local' }],
  ['地图用 transient_local 发',
    { reliability: 'reliable', depth: 1, durability: 'transient_local' },
    { reliability: 'reliable', depth: 1, durability: 'transient_local' }],
];

for (const [name, pub, sub] of cases) {
  const why = compatible(pub, sub);
  demo.log(`${why.length ? '✗' : '✓'} ${name}`);
  why.forEach(w => demo.log('     ', w));
}
demo.log('');
demo.log('注意第 3 条：两边都没写错，只是语义不同 —— 这正是最难查的那种 bug。');

排查套路

发现「订阅了但收不到」时，按这个顺序：

  1. ros2 topic list —— 话题名对不对？（大小写、前导斜杠）
  2. ros2 topic info <名> --verbose —— 两边的 QoS 是多少？
  3. ros2 topic hz <名> —— 有数据吗？频率对不对？
  4. ros2 topic echo <名> --qos-reliability best_effort —— 换 QoS 试试
  5. 是不是命名空间 / domain id 不一样？（ROS_DOMAIN_ID）

ps：第 5 条也能解释「同一台机器上两个终端互相看不见」。

3. tf2：所有坐标挂在同一棵树上

为什么要有它

机器人的任何一个数据都带坐标系：

  • 「前方 1 米有障碍」—— 相对哪个前方？雷达的？底盘的？地图的？
  • 机械臂要抓杯子 —— 杯子在相机坐标系里，但关节要在地基坐标系里动。

tf2 就是那本「坐标系之间怎么换算」的账本。

两条规则

  1. 不能有环：每个坐标系只能有一个父节点。 出现环会直接报「TF_OLD_DATA」之类让人看不懂的错。
  2. 每个变换都要带时间戳：机器人是在动的， 「三秒前的 base_link 在哪」和「现在的 base_link 在哪」是两个答案。
bash
ros2 run tf2_ros tf2_echo base_link camera_link   # 实时看两个坐标系的关系
ros2 run tf2_tools view_frames                     # 导出整棵树

常见故障：时间戳不同步。多机系统里记得装 chrony / ntp， 仿真里则要确认 use_sim_time 一致。

静态变换 vs 动态变换

静态动态
谁会动传感器装在底盘上，相对位置固定关节、底盘相对地图
发布方式static_transform_publisher每个周期发一次
开销只发一次，transient_local持续占用带宽

把固定的东西做成动态的发，是最常见的浪费。

4. 天天要用的那几个工具

命令行

bash
ros2 topic list / info / hz / echo / pub      # 话题
ros2 node list / info                          # 节点
ros2 service list / call                       # 服务
ros2 action list / send_goal                   # 动作
ros2 param list / get / set                    # 参数
ros2 bag record -a / play / info               # 录与放
ros2 launch <pkg> <file.launch.py>             # 起一堆节点
ros2 doctor --report                           # 体检
ros2 run <pkg> <exe> --ros-args -r __ns:=/robot1   # 改名/改命名空间
  • hz 是排查里最省事的一条：先看有没有数据，再看数据对不对。

图形工具

工具干什么
rqt_graph画出节点/话题的图，看连接问题的第一站
rqt_plot曲线看数值话题
rqt_console汇总各节点的日志
rviz2三维可视化：点云、TF、路径、Marker
ros2 bag + rqt离线复现现场

rviz2 里把 TF 打开，很多「数据看起来不对」的问题会立刻现形： 坐标系错位的时候，点云会飞出去。

日志与参数

cpp
RCLCPP_INFO(get_logger(), "开始标定，样本 %d 帧", n);
RCLCPP_WARN(get_logger(), "里程计超期 %.0f ms", dt);
  • 用分级：DEBUG 平时关掉，出问题再开。 --ros-args --log-level debug 一行就能开。
  • 参数用 declare_parameter 声明默认值，运行时可以 --ros-args -p k:=v 覆盖。 别把可调的东西写死在代码里。

launch 文件：把一堆节点当一件事

python
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    return LaunchDescription([
        Node(package='camera', executable='camera_node',
             parameters=[{'fps': 30}], namespace='robot1'),
        Node(package='detector', executable='detect_node',
             remappings=[('/image_raw', '/robot1/image_raw')]),
    ])
  • namespace 做隔离（多台机器人），remappings 做接线。
  • 这才是 ROS 真正的配置面：节点的代码不用改，接线在 launch 里换。

小结

  1. 通信方式按「频率 / 要不要等 / 是不是长任务」三问来选。
  2. QoS 是契约：不兼容就没有连接，而且默认不报错 —— 排查第一步永远是 topic info --verbose。
  3. tf2 是一棵树，不能有环，每个变换都要带时间戳。
  4. 工具不用多，rqt_graph + topic hz/echo + rviz2 就能覆盖八成问题。
